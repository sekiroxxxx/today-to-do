# 刷日常 · 开发流程规范

从 v1.0 到 v1.1 的 20 条实战经验。

---

## 一、开发流程

### 1. 按依赖链排序，逐功能验收
不批量交付，不跳跃。写完一个云函数/组件 → 验收通过 → 再写下一个。

**反例**：一口气写完所有云函数，发现前面的数据模型错了，后面全部重写。

### 2. 每个交付附带验收清单
格式：调什么命令 → 看什么结果 → 查数据库哪条记录。没有验收清单的交付等于没交付。

### 3. API 层先行
所有云函数调用封装到 `utils/api.js`。页面代码只调 `api.xxx()`，不直接写 `wx.cloud.callFunction`。接口层是前后端合同。

### 4. Level 分批推进
顺序：数据层 → 组件层 → 页面重构 → 性能收尾。上层依赖下层，不跳跃不并行。

### 5. 纯函数模块早拆
和外部环境（数据库、云函数上下文）无关的逻辑独立成文件。后续前端化只需复制，不需重写。

## 二、Bug 管理

### 6. 三维度优先级打分
公式：`严重度 × 2 + 影响面 × 1 + 修复成本 × (-1)`。
- 总分 ≥ 7 → P0 致命，立刻修
- 4~6 → P1 重要，本周修
- ≤ 3 → P2 可延，下版本

### 7. 按根因归类批修
拿到 bug 列表后先归类：哪些共享同一个根因。修一个根因消掉多个 bug。不逐条修。

### 8. 测试用例清单 + 线路化
按用户路径组织测试（新用户从零开始、求职全流程、跨 Tab 一致性…）。每次只跑一条线，不随机点。

## 三、需求 → 方案 → 开发

### 9. 需求确认后再入文档
讨论完需求不等于确定。确认结论 > 更新需求文档 > 再进入方案设计。

### 10. 方案逐条对需求打勾
生成开发方案后，逐条对照需求文档检查覆盖度。每一条需求必须对应到至少一个方案条目。

### 11. 方案条目附带验收标准
格式："打开 X 页面 → 看到 Y → 点击 Z → 发生 W"。验收标准写在方案里，不是靠记忆。

### 12. 先确认方向再生成详细方案
不要直接出大方案然后漏需求。先给方向性框架 → 用户确认 → 再展开全部细节。

### 13. 跨层改动先画数据流
改动涉及云函数↔前端数据传递时，写代码前画一张流向图：

```
云函数: addTask
  入参: { title, module }
  写入: custom_tasks { module: event.module || 'custom' }
  返回: { task: { module } }

前端: 创建页
  传参: api.addTask({ title, module: selectedModule })
  读取: res.task.module
```

5 分钟画完，少一个"忘了传字段"的 bug。

### 14. 改动影响清单
交付方案里加一行"受影响的文件"。改云函数返参时列出所有读它的前端页面：

```
改动: generateDailyActions 返参加 module
受影响:
  ☐ pages/today.js · loadTodayActions · 检查读取逻辑
  ☐ pages/progress.js · loadModuleDaily · 检查读取逻辑
  ☐ cloudfunctions/getTodayActions · 检查兼容旧数据
```

## 四、设计 → 代码

### 13. 原型先行
UI 布局的讨论在 HTML 原型上完成。原型改方向零成本，代码改方向重写四个文件。

### 14. 原型 → 代码的组件映射表
原型完成后，先出一张对照表再写代码：
```
原型元素        →  代码组件       →  关键属性
.exec-task-card →  module-task   →  { badges: [], actions: [...] }
.funnel-row     →  slot-data     →  求职=漏斗，工作=统计
```

---

### 5. 页面/组件内：视觉层先于逻辑层
WXML → WXSS → 静态数据绑定 → JS 逻辑。先把界面搭出来，用假数据确认布局和样式正确，再接入真实数据和交互。

**为什么减少 bug**：
- WXML/WXSS 的布局错误不依赖 JS 就能发现
- JS 报错时界面仍然可见，不会白屏排查困难
- 视觉层是"规格说明"——写 JS 时数据该长什么样已经有参照

**反例**：一口气写完 WXML+WXSS+JS，打开白屏，不知道是 WXML 结构错了还是 JS 报错了还是数据没返回。

### 6. 组件/页面写 JS 前先穷举状态
每个组件至少有以下状态，写 WXML 时每个状态一个 `wx:if`，不遗漏：

```
module-task 状态穷举：
  ☐ 正常进行中（标题+描述+按钮）
  ☐ 已完成（灰掉+删除线+无按钮）
  ☐ 加载中（骨架屏）
  ☐ 操作中（按钮显示"..."+disabled）
  ☐ 空数据（模块无任务）
```

很多 bug 是"忘了一个状态"——完成了没样式、加载中没遮罩。穷举一次，6 个状态都写到 WXML 里。

## 七、交付粒度

### 21. 一个可验收的改动 = 一次交付

不批量交付。一次交付的工作量控制在 5 分钟内能验收完。超过就拆。

每次交付必须包含：改了什么文件、改了什么内容、验收步骤、通过标准、关联的需求条目。

### 22. 通过才提交

验收通过 → 提交 git → 下一个交付。Git 历史 = 验收记录链。不通过 → 修 → 再验收。修了两次还不过 → 回滚重新设计。

### 23. 回归节奏

每 5 个交付跑一次全链路回归，确保新改动没打坏旧功能。

---

# 速度总结

```
开发 → 粒度小 → 验收快 → bug 早发现 → 少返工 → 整体更快
开发 → 粒度大 → 验收迟 → bug 堆积 → 定位难 → 返工多 → 整体更慢
```

---

## 五、技术约束

### 15. WXML 表达式限制
`{{ }}` 内只放变量名或简单三元表达式。不支持 `.toFixed()`、`[0]`、`.trim()` 等 JS 方法。需要计算的值在 JS 里算好再 `setData`。

### 16. 脏标记缓存
`app.globalData.dirty` 控制 Tab 页面的数据刷新。数据没变 → 不发云函数请求。只在增删改操作后置脏。

## 六、协作规范

### 17. 需求会话 vs 代码会话
- 需求会话：讨论产品逻辑、设计方向、方案设计、bug 分析
- 代码会话：写代码、修 bug、验收
- 两个会话互不污染上下文

### 18. AI 输出清单的自检
AI 输出"完整清单"时必须：
1. 先逐条过需求文档
2. 明确说明"共 N 条，已覆盖 M 条，未覆盖 K 条"
3. 附对照表
用户不做 AI 的查漏工作。

### 19. 方案生成后的确认流程
1. AI 生成方案 → 列出覆盖对照
2. 用户检查遗漏 → 补充
3. AI 重新生成完整版
4. 用户最终确认 → 进代码会话开发

### 20. 概念纠错前置
需求讨论阶段发现模型错误（如画像→模块）→ 立即转向。越早纠正代价越小。
